Executive summary

GDPR is not switched off by being a small, unpublished, non-commercial student project. The "purely personal activity" exemption is narrow and personal — it doesn't cover a team providing software to others [1][2] verified. No carve-out exists for student/course projects.

The single most actionable, Norway-specific finding: Sikt's notification duty is explicitly scoped on its own site to research, not ordinary coursework — each institution decides which project types are covered [11] verified, direct quote. This is not automatically a research project. Ask the course coordinator or institution's Sikt/personvern contact directly.

The practical path that sidesteps most complexity: test and grade primarily against fictional/synthetic data — per Helsedirektoratet, genuinely fictional data isn't personal data at all [13] medium-high, single source. If a real team member logs real data, get explicit opt-in consent first; diet/weight/training logs aren't automatically special-category but regulators lean broad, especially for longitudinal data [4][5][6].

For the PRD: data minimization + a working deletion path from day one [9][10]; a short plain-language consent screen if real data is ever entered [18][8]; deletion doesn't need to be instant or automated — real small OSS fitness trackers use manual request flows [23][27][28].

GDPR applicability & special-category health data

GDPR's personal/household exemption (Art 2(2)(c)) covers purely private activity with no professional connection, but Recital 18 states the Regulation "still applies to controllers or processors that provide the means for processing personal data" for those activities [1][2]. CJEU case law reads this narrowly [3] medium. For this project: a team member logging only their own data sits close to the exempt line; the moment anyone else uses the app, GDPR applies.

Diet/weight/exercise data is not automatically special-category (Art 9) — only when it reveals actual health status [4] — but WP29 (2015) and EDPB Guidelines 03/2020 both lean toward a broad reading for longitudinal fitness data [5][6] medium. Defensible default: treat it as special-category. If so, explicit consent (Art 9(2)(a)) is the simplest basis [7], requiring a real affirmative act per EDPB Guidelines 05/2020 [8]. Baseline obligations apply regardless: data minimization, storage limitation (Art 5), right to erasure (Art 17) [9][10] verified.

Datatilsynet / Sikt — what actually applies in Norway

No Datatilsynet.no guidance specifically for small/hobby/student projects was found (unlike Denmark's Datatilsynet) — negative finding, low confidence. An EDPB SME guide exists in Norwegian but isn't Datatilsynet's own [14].

Load-bearing finding: Sikt's own page states its personverntjenester is "for forsking" (for research), with students covered only "i forsking," and each institution decides which project types are reported [11] verified — direct primary quote. University pages describe thesis/research projects, not ordinary course assignments specifically [15] medium.

Genuinely fictional/synthetic data appears to fall outside GDPR entirely per Helsedirektoratet's Normen guidance [13] medium-high, single source. For real team members' own real data in a shared/gradable system, no Norway-specific guidance was found; the EU household exemption probably doesn't cleanly apply [17] — this research's own inference, not a direct ruling.

A concrete, workable consent / minimization / deletion pattern

Consent: one short screen, separate from general ToS, naming what's collected and why, granular per purpose where practical, no pre-ticked boxes, easy withdrawal [18][8].

Minimization: only collect fields a current feature uses (Art 5(1)(c)) [21]; age-band-not-DOB is widely echoed practitioner practice, not confirmed regulator doctrine [22] unverified. Open Trackers achieves minimization architecturally via local-first storage [23].

Deletion: Art 17's "without undue delay" benchmarks to one month [10]; a flag-only soft delete that never progresses to real removal is non-compliant per Danish DPA guidance [24]. A short, bounded soft-delete window followed by actual hard delete is legitimate practice [25]. Real small OSS fitness trackers (MyTracker, Lettest) route deletion through a GitHub issue, not an automated pipeline [27][28] — a soft-delete button + manual follow-up would already match or exceed this.

Cross-dimension insight

All three dimensions converge on the same architecture decision from different angles: EU law treats "student project" as legally irrelevant to applicability [1][2]; Norwegian Sikt guidance treats "course not research" as relevant to a different, narrower notification duty [11]; real small OSS apps treat "we're small" as a reason to keep the implementation simple, not a reason to skip the obligation [23][27][28]. Scope the rigor to project size; don't scope the right to ask, or the honesty of the text, down to zero.

Recommendations

  1. Default to fictional/synthetic test data for grading and demos. medium-high confidence
  2. If any real team member logs real data, get explicit opt-in consent first — treat it as special-category (Art 9) to be safe. high on mechanism, medium on the Art 9 default
  3. Build data minimization and a real deletion path in from day one — soft-delete + manual/scripted hard-delete shortly after is legitimate. high confidence
  4. Ask the course coordinator or institution's Sikt contact whether this course falls under the institution's Sikt agreement — the one question only they can answer. high confidence this is the right next step
  5. Frame it in the PRD as "low enforcement risk," not "GDPR doesn't apply." The latter misrepresents the law. high confidence

Open questions

  • Does this course's Sikt agreement cover graded coursework, or only research? The single most actionable open item — only the institution can answer.
  • Is lightly-modified "synthetic" data (based on real people) still exempt? Not addressed by any source found — a caution, not a finding.
  • What does a Norway-specific minimal consent text need to say? No Datatilsynet-authored template found; only EU/UK/Danish sources.
  • Is age-range-not-DOB regulator-endorsed or just convention? No regulator source found making this comparison for fitness apps.
  • What's an appropriate soft-delete grace window? No regulator-stated number exists; one month (Art 17) is the only hard benchmark.

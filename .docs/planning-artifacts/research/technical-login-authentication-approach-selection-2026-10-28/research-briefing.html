Executive summary

Pick: roll-your-own email+password, following OWASP's own checklist, as the v1 default — carried into the PRD as explicit, checkable acceptance criteria, not left implicit.

OWASP's cheat sheets make the bar well-documented and bounded: bcrypt/argon2id hashing, server-side sessions, per-account rate limiting, generic error messages [1][2][3] verified — a day-ish of focused work, not a research problem. The real risk is skipping the less-visible steps under deadline pressure, not hashing itself.

The auth-library category isn't a clear win for this scope — the strongest evidence against it comes from inside the category: Lucia Auth, a comparable thin TS library, is reported (community sources, not independently dated) to have been deprecated by its maintainer around Oct 2024 in favor of teaching roll-your-own; what's directly confirmed is narrower — the library itself now says it no longer provides CSRF protection [5] medium. Every library checked (Flask-Login, Devise, Auth.js) leaves CSRF to the developer and locks the team to one framework [6].

Hosted auth-as-a-service is a genuine runner-up — but only half the category clears the hard gate. Supabase and Firebase both have confirmed local/offline modes [7][8] verified; Clerk and Auth0 do not and fail the no-paid-account/local-run constraint outright [9] cut.

Evidence per candidate

Roll-your-own email+password

OWASP: Argon2id or bcrypt (≥10) for hashing, library-handled salting [1]. Server-side sessions with CSPRNG IDs (≥128 bits) in HttpOnly/Secure/SameSite cookies, not JWT-in-localStorage [2]. The documented common failure modes are missing per-account rate limiting and account enumeration — not hashing itself [3] verified. No authoritative complexity benchmark exists; illustrative tutorials suggest ~100–300 lines [4] low confidence, illustrative.

Self-hosted auth library/middleware

Flask-Login, Devise, and Auth.js all explicitly leave CSRF protection to the developer, and each locks the team to one backend framework [6]. Devise's README documents no sanctioned test-user-seeding path, with a Confirmable-module trap for directly-created accounts. Auth.js's own docs now note the project "is now part of Better Auth," signaling mid-transition. The strongest signal: Lucia Auth is reported to have been deprecated by its maintainer (community-sourced, unconfirmed date) in favor of teaching roll-your-own for exactly this scope; directly confirmed is only that Lucia's v3 guide says it no longer provides strict CSRF protection [5] medium.

Hosted auth-as-a-service

Supabase clears the local/offline gate: supabase start runs the full stack incl. Auth via Docker; Supabase's own docs market "offline work" as a feature [7] verified. Firebase also clears it via Local Emulator Suite "demo" projects requiring no real Firebase project — though a misconfigured client silently falls back to live production [8] verified. Clerk and Auth0 do not: Clerk's "accountless" flow still calls Clerk's servers; Auth0 has no official local mode [9] cut. For the two viable vendors: Docker is a heavier install [10], real-credential seeding needs a pgcrypto pattern with a documented friction issue [11], and Supabase's free tier auto-pauses after ~a week of inactivity [12].

Verdict

Pick: roll-your-own email+password, built to OWASP's cheat sheets. Runner-up: hosted auth via Supabase/Firebase local mode — genuinely close, worth revisiting once the stack is chosen. Not recommended right now: a generic self-hosted auth library — coupled to an unchosen framework, with the one directly comparable library (Lucia) reported deprecated for this exact scope.

Strongest argument against the pick: under deadline pressure, a team might skip the less-visible steps (rate limiting, error-message hygiene, cookie flags) precisely because no library enforces them. Mitigation: carry the OWASP checklist into the PRD as explicit acceptance criteria.

Cheapest reversibility hedge: isolate auth behind a small service interface (authService.login()/register()/logout()) so switching to Supabase/Firebase local auth later costs an implementation change, not a rewrite.

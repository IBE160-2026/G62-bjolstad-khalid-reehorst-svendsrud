- (decision) Plan approved: technical research, select shape, 3 approach categories (roll-your-own email+password, stack-appropriate auth library/middleware researched generically by pattern, hosted auth-as-a-service with free local-dev tier). Dimensions: landscape/maturity, implementation reality (password hashing, session vs JWT, seeding test users safely), ecosystem health. preset=standard (3 subagents, 8 sources/round, depth 2), validation=normal. Requirements frame from brief.md/prep doc constraints (no paid accounts, local runnable, seeded test users), not web research.
- (source) Roll-your-own dimension, round 1: 9 sources (OWASP Password Storage, Authentication, Session Management Cheat Sheets, OWASP Top 10 A07:2021, CloudBees/dev.to practitioner writeups, node-auth-skeleton + freeCodeCamp/Honeybadger tutorials, Rails/MITRE Vulcan seed-user guidance).
- (claim) ref=1 status=verified class=security pub=2026-10 — OWASP recommends Argon2id (or bcrypt work factor >=10 / scrypt as fallback) for password hashing, with per-user salting handled automatically by the library; fast hashes like SHA-256 are unsuitable. Confirmed directly against OWASP Password Storage Cheat Sheet (primary).
- (claim) ref=2 status=verified class=security pub=2026-10 — OWASP recommends server-side sessions (CSPRNG session ID >=128 bits, HttpOnly+Secure+SameSite cookie) over JWT-in-localStorage for a small app; JWT revocation is flagged as an open problem by OWASP's own Session Management Cheat Sheet.
- (claim) ref=3 status=verified class=security pub=2026-10 — OWASP Top 10 A07:2021 and the Authentication Cheat Sheet identify missing per-account rate limiting and account-enumeration via differing error messages as the common real-world failure modes, not password hashing itself.
- (claim) ref=4 status=unverified class=implementation pub=2026-10 — no authoritative LOC/time-complexity benchmark exists for a minimal roll-your-own auth implementation; illustrative tutorials suggest ~100-300 lines but this is not a measured source. No OWASP-tier source specifically addresses seeding test/grading credentials either — practitioner consensus only (environment-gated, flagged seed accounts).
- (source) Auth-library dimension, round 1: 12 sources (Flask-Login docs, Devise README, Auth.js/Better Auth docs, Lucia deprecation + migration guide, Clerk build-vs-buy article, Django/pytest-django seeding guides).
- (source) Hosted-auth-service dimension, round 1: 14 sources (Supabase local-dev + free-project-pausing docs, Firebase emulator-suite docs, Clerk accountless blog, Auth0 community thread + localauth0, seeding guides for both).
- (claim) ref=5 status=verified class=implementation pub=2024-10 — Lucia Auth's own maintainer deprecated the library in Oct 2024, concluding a thin auth library didn't clearly beat teaching roll-your-own for this kind of scope; strongest outside signal that library-vs-rollown is a close call for small email+password-only apps.
- (claim) ref=6 status=verified class=implementation pub=2026-10 — every self-hosted auth library examined (Flask-Login, Devise, Auth.js/Better Auth) explicitly leaves CSRF protection to the developer; this is not library-specific but a common gap across the category, confirmed directly against each library's own docs.
- (claim) ref=7 status=verified class=compatibility pub=2026-10 — Supabase's local CLI stack (via Docker) runs the full stack including Auth fully offline/locally with throwaway local keys, confirmed directly against Supabase's own docs (primary). This is the only hosted-auth-service candidate that clears the no-paid-account/local-run hard gate comfortably.
- (claim) ref=8 status=verified class=compatibility pub=2026-10 — Firebase's Local Emulator Suite supports demo projects with no real Firebase config/live resources, confirmed directly against Firebase's own docs; but silently falls back to live production if a client isn't explicitly pointed at the emulator.
- (claim) ref=9 status=verified class=compatibility pub=2026-10 — Clerk and Auth0 do NOT have a genuine local/offline mode; Clerk's accountless flow still calls Clerk's servers and routes all auth traffic through its hosted API; Auth0 has no official local mode, only unofficial third-party simulators. Both fail the hard gate for this project.
- (claim) ref=10 status=unverified class=implementation pub=2026-10 — seeding real email+password test users (not just bare DB rows) is a documented soft spot across the board: Devise has no sanctioned seeding path and a Confirmable-module trap; Supabase needs a pgcrypto+auth.identities pattern with at least one open GitHub issue reporting friction; Firebase's emulator import/export mechanism is only secondary-sourced, not pinned to one official page.
- (event) research.md assembled: 3 candidate categories, Clerk/Auth0 cut within hosted-service category (fail local/offline hard gate), decision matrix built, pick=roll-your-own (23/25), runner-up=hosted Supabase/Firebase (22/25), auth-library category last (12/25) driven by framework coupling + Lucia deprecation precedent. Citations verified clean (12/12).

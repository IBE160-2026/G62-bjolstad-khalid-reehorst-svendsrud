Executive summary

Pick: Quagga2 (@ericblade/quagga2), on condition that the team runs the mobile spike it already planned before locking in the architecture.

No candidate has confirmed-good iOS Safari reliability — that's the one finding that cuts across everything else. html5-qrcode has the strongest confirmed-bad signal: four users report the same unresolved iOS barcode-scanning failure in one GitHub issue, one quantifying it under 10% recognition on iPhones [3] medium confidence; the rest are simply unverified in either direction.

Given that, the decision comes down to the next-strongest signals: Quagga2 is the only candidate that is both actively maintained (commit today, release one week ago [23][24]) and ships a working camera-capture pipeline out of the box [22] verified. zxing-wasm matches it on maintenance but is decode-only and would need a hand-built camera UI [12]; @zxing/library ships a camera wrapper but its maintenance signal is weaker (self-described "maintenance mode," a 20-month release gap before two releases landed in April 2026) [6][8]. The native BarcodeDetector API is cut outright — disabled by default in every iOS Safari version through 27.2 [17][18], failing the "works for a real user on an unmodified phone" gate.

Biggest caveat: Quagga2's own iOS Safari EAN-13 reliability was not directly evidenced either way this session [25] unverified — the pick rests on the criteria that were evidenced, not on a confirmed iOS win. The team's already-planned mobile spike is the test that actually settles this.

Evidence per candidate

html5-qrcode

Nominally passes every hard gate — a platform-support table marks iOS Safari and Android Chrome as fully supported, EAN-13 is listed, Apache-2.0 license [1][2]. In practice, a GitHub issue open since April 2024 collects four independent users reporting the same unresolved iOS barcode-scanning failure on iPhone 13/15 — one quantifies <10% recognition, three others report "same problem" without numbers; none confirms the format tested was EAN-13 specifically [3] medium confidence. No substantive commit since April 2023; maintainer calls it "maintenance mode," 448 open vs 334 closed issues [2] verified. Easiest integration of all five (fewer than ten lines, built-in UI) [1] — doesn't offset the 2.5-year-unaddressed iOS bug.

@zxing/library (zxing-js)

Passes every hard gate via the browser's MediaDevices API [6]. No recent (2025–2026) real-device EAN-13 test found — a gap, not a confirmed problem [6][7][11]. Maintenance is ambiguous: self-described "maintenance mode" yet two releases landed April 2026 after a 20-month gap [6][8] semi-active.

zxing-wasm

Fails the camera-API gate standalone — decode-only, no getUserMedia wiring; wrapper libraries or a (still "planned") React toolkit are needed for camera UI [12] partial fail. Decodes EAN-13, free/OSS [12]. The most actively maintained candidate — release 6 days before this research, commit the same day [13] verified. Its "WASM is faster than pure JS" pitch could not be corroborated by independent non-vendor sources [14] unverified.

Native BarcodeDetector API — cut

Meets every gate on Android [20][21]. On iOS Safari: "disabled by default" in every version 17.0–27.2 on caniuse.com, corroborated by WebKit's bug tracker (implementation "unusable," plus an open, unresolved regression even with the flag manually enabled) [17][18][19] verified — 2 independent sources. An ordinary iPhone user cannot use this API. The leading polyfill is itself built on zxing-wasm [12] — "going native" doesn't avoid a WASM dependency once iOS is in scope.

Quagga2 (wildcard, screened in round 2)

Surfaced independently by two separate research assistants. Screening confirmed — not just assumed — every hard gate, including a built-in getUserMedia camera pipeline and EAN-13 reader [22] verified. Most recently active candidate alongside zxing-wasm: release 6 days before this research, commit the same day, ~monthly cadence over the past year [23][24] verified. No disqualifying red flags. The one unresolved point: no direct evidence, positive or negative, for Quagga2's own EAN-13 reliability on a real iPhone — the only adjacent signal concerns the original pre-fork QuaggaJS, not Quagga2 itself [25] unverified — biggest open question.

Verdict

Pick: Quagga2. Runner-up: zxing-wasm and @zxing/library, tied — zxing-wasm if comfortable building a camera UI and wanting the most active decode core; @zxing/library for a more complete, if staler, package. html5-qrcode is not recommended given its confirmed, multi-user, 2.5-year-unaddressed iOS problem. Native BarcodeDetector is cut for this cross-platform requirement.

Strongest argument against the pick: Quagga2's own iOS Safari EAN-13 reliability has no direct evidence either way — it could still fail completely on real hardware. Not a reason to pick differently (none of the alternatives has better iOS evidence), but a reason to treat the pick as provisional.

Cheapest reversibility hedge: wrap scanning behind a small adapter (a single scanBarcode() interface) so swapping libraries later — if the spike shows Quagga2 failing — costs an implementation change, not a UI rewrite.

Open questions

  • Quagga2's real-device iOS Safari EAN-13 reliability — the decision's single biggest unknown. Next step: the team's planned mobile spike, Quagga2 first.
  • zxing-wasm's "WASM is faster" claim — not corroborated independently. Doesn't affect the pick, but matters if re-weighing toward it.
  • @zxing/library's maintenance trajectory — one-off releases or a resumption? Watch the repo for a few more months.
  • Quagga2 and zxing-wasm bundle sizes — blocked by rate limits this session. Retry, or measure via local build output.
  • Android reliability across all four finalists — thin evidence everywhere. Worth a quick real-device check alongside the iOS spike.
